# PRD-04. 찜(즐겨찾기) 기능

## 1. 배경/목표

사용자가 마음에 드는 추천 코스(또는 개별 장소)를 저장해두고 나중에
다시 보거나 비교할 수 있게 한다. 사용자가 명시적으로 요청한 핵심
기능이며, 로그인 여부와 관계없이 끊김 없이 사용할 수 있어야 한다.

## 2. 사용자 스토리

- 사용자로서, 로그인하지 않아도 마음에 드는 코스를 일단 찜해두고 싶다.
- 사용자로서, 나중에 로그인하면 찜한 목록이 그대로 이어지길 바란다.
- 사용자로서, 코스 전체뿐 아니라 코스 안의 특정 장소만 따로 찜하고 싶다.
- 사용자로서, 찜 목록에서 코스를 다시 열어보고, 필요하면 일부 장소를
  바꿔 재구성하고 싶다.
- 사용자로서, 찜을 취소하면 즉시 목록에서 사라지길 바란다.

## 3. 기능 정의

- **찜 대상 단위 2가지**를 지원한다.
  1. **코스 찜**: 추천받은 코스 전체(제목, 일자별 스팟 순서 포함)를 저장
  2. **장소 찜**: 코스 여부와 무관하게 개별 장소(맛집/카페/관광지/숙소)
     하나만 저장
- 찜 버튼은 코스 카드, 코스 상세 화면, 장소 상세 화면 각각에 노출되며
  대상에 맞게 코스 찜/장소 찜을 구분해 저장한다.

## 4. 기능 요구사항 (MoSCoW)

**Must**
- 비로그인 사용자: 찜 데이터를 브라우저 로컬 저장소(localStorage)에 저장
- 로그인 시: 로컬 저장된 찜 데이터를 서버 계정 데이터와 병합(중복 제거
  후 합집합)하여 이후부터는 서버 기준으로 동기화
- 찜 목록 화면: 코스 찜 탭 / 장소 찜 탭 구분 표시
- 찜 추가/취소는 별도 확인창 없이 즉시 반영(하트 아이콘 토글), 실행취소
  (undo) 스낵바 제공
- 찜한 코스 상세에서 "이 코스로 다시 계획하기"(재구성 요청 → AI 코스
  추천 파이프라인 재호출) 진입 가능

**Should**
- 찜 목록 정렬(최근 찜한 순/이름순), 필터(테마별)
- 찜한 장소가 나중에 폐업/휴업 처리되면 목록에 상태 뱃지 표시

**Could**
- 찜 목록 공유(링크로 타인에게 공유) — 2차 검토

## 5. 데이터 모델 (예시)

```json
// 로컬(localStorage) / 서버 공통 구조
{
  "favorites": {
    "courses": [
      {
        "course_id": "course_abc123",
        "title": "감성 카페와 물멍 스팟으로 채운 두물머리 힐링 코스",
        "preset_type": "couple",
        "saved_at": "2026-09-12T10:00:00+09:00",
        "itinerary_snapshot": { "...": "찜 시점의 코스 스냅샷(가격/시간 변동 대비)" }
      }
    ],
    "places": [
      { "place_id": "nvr_789012", "name": "두물머리 뷰 카페", "saved_at": "2026-09-12T10:05:00+09:00" }
    ]
  }
}
```

- `itinerary_snapshot`을 저장하는 이유: 이후 영업시간/폐업 등으로 원본
  코스 데이터가 바뀌어도, 사용자가 찜한 시점의 코스를 그대로 볼 수 있게
  하기 위함(최신 상태는 별도 뱃지로 안내).

## 6. 화면/UX 요구사항

- 하단 탭바(모바일) 또는 상단 네비게이션(데스크톱)에 "찜" 메뉴 상시 노출,
  찜 개수 배지 표시
- 찜 버튼은 어디서든 동일한 아이콘(하트)과 인터랙션(탭 시 애니메이션)
  으로 통일
- 빈 찜 목록 상태에서는 추천 프리셋 화면으로 유도하는 CTA 표시

## 7. 데이터/연동 요구사항

- 서버 저장소는 **Cloud Firestore**를 사용한다. 로그인 사용자 기준으로
  `users/{uid}/favoriteCourses/{courseId}`, `users/{uid}/favoritePlaces/{placeId}`
  하위 컬렉션 구조로 저장하며, 각 사용자는 자기 문서만 읽기/쓰기 가능
  (Firestore Security Rules) — 상세 스키마·보안 규칙은
  [`06-infra-deployment-prd.md`](./06-infra-deployment-prd.md) §3~4 참조
- 로그인 여부 판별은 **Firebase Authentication**을 사용
- `01-ai-course-recommendation-prd.md`의 코스 데이터 스키마와 필드
  호환 유지(찜 시 별도 변환 로직 최소화)

## 8. 비기능 요구사항

- 로컬→서버 병합 시 데이터 유실 없어야 함(병합 실패 시 로컬 데이터
  유지, 재시도)
- 찜 토글 반응 속도 체감 지연 없이 즉시(낙관적 업데이트) 처리

## 9. 성공지표

- `00-overview-prd.md`의 찜 전환율(≥25%), 재방문율(≥15%) KPI와 동일
- 찜 후 7일 내 "이 코스로 다시 계획하기" 사용률

## 10. 오픈 이슈

- 비로그인 상태의 찜 데이터 보관 기한(브라우저 데이터 삭제 시 유실 —
  로그인 유도 배너 노출 시점 결정 필요)
- 코스 스냅샷과 최신 데이터 간 불일치 시 사용자에게 어떻게 안내할지
  (예: "일부 정보가 변경되었어요" 배너) 세부 문구/UX 확정 필요
