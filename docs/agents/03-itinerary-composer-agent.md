# 3. 코스 플래닝(동선 최적화) 에이전트 (Itinerary Composer Agent)

## 역할/책임

카테고리별 후보 장소 리스트를 받아, 일정(며칠, 하루 몇 곳)과 이동수단을
고려해 지리적으로 자연스러운 동선의 Day1/Day2… 코스를 구성한다. 실제
거리/이동시간 계산은 LLM이 직접 하지 않고 지도 API 도구를 호출해
받아오며, LLM은 "어떤 조합이 자연스러운 여행 흐름인지"(아침-관광,
점심-맛집, 오후-카페, 저녁-맛집, 숙소 순서 등) 판단만 담당한다.

## 기준 여행자: 서울에서 출발하는 사람

이 서비스의 코스는 **서울에서 출발해 서울로 돌아가는 사람**을 기준으로
짠다. 그래서 시간대는 템플릿에 적힌 고정값이 아니라, 출발 시각에서
시작해 아래를 사슬처럼 이어 계산한다 (`src/lib/agents/schedule.ts`).

```
도착 = 직전 지점 종료 + 이동시간
시작 = max(도착, 식사 시작 하한)
종료 = 시작 + 체류시간
```

| 항목 | 값 |
| --- | --- |
| 서울 출발(당일치기·1일차) | 09:00, 서울시청(37.5665, 126.978) 기준 |
| 숙소 출발(2일차 이후) | 10:00 — 전날 묵은 숙소가 그날의 출발지 |
| 체류시간 | 관광지 90분 · 식당 70분 · 카페 60분 · 숙소 체크인(종료 없음) |
| 식사 시작 하한 | 그날 첫 식당 = 점심 11:40 · 두 번째 식당 = 저녁 17:00 |
| 이동시간 | 직선거리 × 거리대별 평균 속도 (5km 미만 22 / 20km 미만 32 / 그 이상 42km/h), 5분 단위 |

마지막 날 마지막 스팟 뒤에는 서울로 돌아오는 시각(`ItineraryDay.arrival`)이
붙는다. 숙소에서 하루를 마치는 날에는 붙지 않는다. 하루의 출발은
`ItineraryDay.departure`, 스팟마다 직전 지점에서 오는 시간은
`ItineraryStop.travelMinutes`로 내려간다.

거리대로 평균 속도를 나누는 이유는 한 값으로는 양쪽을 다 망치기 때문이다
— 양평 안의 국도를 기준으로 잡으면 서울~양평이 두 시간이 되고,
고속도로를 기준으로 잡으면 읍내 안을 5분 만에 가는 것으로 나온다.
직선거리에 적용하는 값이라 우회·신호 대기가 이미 녹아 있다.

## 하루 뼈대

| 일정 | 순서 |
| --- | --- |
| 당일치기 | 관광지 → 점심 → 관광지 → 카페 → 저녁 |
| 1박 2일 1일차 | 위와 같고 끝에 숙소 |
| 마지막 날 | 관광지 → 점심 → 카페 (서울 복귀 시간을 남긴다) |

슬롯마다 후보를 4곳 받아 **직전 지점(그날 출발지 또는 앞 스팟)에서 가장
가까운 곳**을 고른다. 후보는 이미 취향 점수순이므로, 결과는 "취향에 맞는
곳들 중 동선이 짧은 곳"이 된다.

슬롯의 카테고리에 쓸 수 있는 후보가 하나도 없으면 **대체 카테고리**에서
고른다(관광지 ↔ 카페). 반려동물 동반 조건이 그렇다 — 동반 가능 업소 현황에
음식점·카페만 있어 동반 가능한 관광지가 0곳이고, 그 자리를 비우면 점심과
저녁 사이가 통째로 빈 코스가 된다. 식당 자리는 대체하지 않는다(끼니 수가
늘어난다). 후보가 있는 카테고리는 이 경로를 타지 않아 일반 코스는 그대로다.

## 사용 가능한 Tool/외부 API

- **네이버 지도 Directions 5 API (Naver Cloud Platform)** — 두 지점 간
  자동차 이동시간·거리 계산
- **ODsay 대중교통 길찾기 API** — 대중교통(버스/지하철) 이동시간 계산
  (네이버는 대중교통 길찾기 API를 제공하지 않아 별도 연동 필요,
  `07-external-api-integration.md` 참조)
- 내부 함수 `driveMinutes(from, to)` — 위 두 API가 열리기 전까지 쓰는
  직선거리 어림값 (`src/lib/agents/schedule.ts`)

## System Prompt 초안

```
당신은 여행 동선 설계 전문 에이전트입니다. 카테고리별 후보 장소 중에서
하루 일정에 맞게 장소를 선택하고 방문 순서를 배정하세요.

규칙:
- 여행자는 서울에서 아침에 출발해 마지막 날 서울로 돌아갑니다. 서울에서
  오가는 이동시간과 각 장소의 체류시간을 일정에 반드시 포함하세요.
- 하루에 숙소 1곳(마지막), 식사(맛집) 1~2회, 카페/관광지는 취향에 따라
  배분합니다.
- 인접한 장소끼리 묶어 이동 거리를 최소화하세요. 실제 이동시간은
  제공된 도구로 조회한 값을 사용하고 임의로 추정하지 마세요.
- 마지막 날은 숙소를 포함하지 않고, 서울로 돌아갈 시간을 남깁니다.
출력은 JSON만 반환하세요.
```

## 다른 에이전트와의 관계

- 2번(장소 검색)의 출력을 입력으로 받음.
- 4번(검증)에게 초안 코스를 전달하고, 검증 실패 시 4번의 피드백(부적합
  장소 및 사유)을 받아 대체 장소로 재구성. 4번이 보는 "배정된 시간"은
  여기서 계산한 실제 시각이라, 서울에서 오는 시간까지 친 결과로 영업
  여부를 따진다.

## 실패/재시도 처리

- 특정 시간대에 배정 가능한 후보가 없으면(예: 카페 후보 소진) 해당
  슬롯을 비우고 오케스트레이터에 "후보 부족" 플래그 전달 → 2번 에이전트
  재호출 트리거.
